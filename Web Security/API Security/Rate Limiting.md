For an unauthenticated **Contact Us** form, use **two independent rate-limit buckets: one keyed by IP and one keyed by an anonymous browser cookie**—not a single combined `IP + cookie` key. The IP limit stops simple bursts from one source, while the cookie limit catches repeated submissions from the same browser even if the IP changes; keeping them separate prevents an attacker from resetting both limits by changing just one signal. Use Redis-backed counters (for example, `express-rate-limit` with `rate-limit-redis`), a sliding-window or token-bucket algorithm, a short limit such as 5 submissions per 15 minutes per IP, and a daily cap; then add a honeypot and a CAPTCHA/bot challenge for suspicious or high-volume traffic. IP and session/cookie limits are both imperfect—IPs can be rotated and cookies can be cleared—so layering them is the practical anonymous-form approach, with server-side validation and monitoring as supporting controls
